## GLG 원문 — 이번 장은 정리하고, 옛 장은 정리본을 줄인다

> 3에서 4로 갈때 1,2를 정리하느라 뭔가 고생을 한다면 말이 안되는 일이야. 인간도 그렇게 안하거든.

> 이 요약정보는 어디에 들어가지? 메타레코드에 json 블록으로 담기는게 간단하리라 보는데, 그래서 메타레코드가 가든아이디의 핵심이며 불변하는 생일 좌표가 되는 것이거든.

**현재 요구 해석:** n→n+1에서 현장 n을 새로 정리하고, 1..n−1은 기존 정리본만 줄인다. renew 준비를 이유로 과거 원본을 재독하지 않는다. 새 장은 직전 작업만이 아니라 언제 무엇을 함께하고 지금에 이르렀는지 층별 얼개를 받는다. 오래된 장은 더 얇고 최근 장은 더 자세하지만, 전체 이력을 컨텍스트에 무제한 누적하지 않는다.

메타레코드에 원본 좌표·시작/끝·정리본을 두는 것이 GLG가 제시한 방향이다. 정확한 키, 상한, 축약 빈도/함수, 모델 호출 횟수, hash 필요 여부는 미결이다. 후속 GLG 지시(6a8b34 전달, NEXT의 GLG 원문 참조)에 따라 정리 주체는 현재 장의 에이전트다(맨 위 "최신 주체와 분담"). 정리 턴을 어떻게 호출할지, 최종 블록과 저장·주입을 어떤 방식으로 할지는 미결이다. 구현과 실행의 승인은 별도다.
