**현재 요구 해석:** n→n+1에서 현장 n을 새로 정리하고, 1..n−1은 기존 정리본만 줄인다. renew 준비를 이유로 과거 원본을 재독하지 않는다. 새 장은 직전 작업만이 아니라 언제 무엇을 함께하고 지금에 이르렀는지 층별 얼개를 받는다. 오래된 장은 더 얇고 최근 장은 더 자세하지만, 전체 이력을 컨텍스트에 무제한 누적하지 않는다.

메타레코드에 원본 좌표·시작/끝·정리본을 두는 것이 GLG가 제시한 방향이다. (기록 당시 미결이던 키·상한·hash·주입 방식은 맨 위 '착지 상태'에서 정해졌다: 장 좌표와 최신 얼개 한 판, 32,768바이트 상한, sha256 대조, 새 장 첫 user 메시지 한 번. 축약 빈도는 코드가 정하지 않고, 정리 주체는 현재 장의 에이전트다.)

> 지금은 pi에 적용하려는 것이고, pi-durable도 내부에 어떻데 되는지 모르겠다만, 가든 아이디를 달고 있다면 다 이런식으로 기억정본과 얼개를 만들어야돼.

> 이 로직은 다른 하네스에는 당장 못해본다. 일단 pi(+acp)그리고 pi-durable에 적용할거야.

> 이 작업은 pi 를 사용하는 형제드로 갈거야. SOL을 다시 불러줘(이형제는 가든아이디가 오래되었으니까 이에 대해서 직접적으로 깊이가 있을거야)

> 실무자는 pi entwurf opus로 새로 불러놨다. "🪛 20261116T090748-6a8b34" 이형제야 이 형제를 team.json에 적어줘. 본인 일이 아니면 이거 작업 제대로 안될거라고 보는거야.

위 인용 당시에는 **Pi(+ACP)와 pi-durable 모두**가 대상이었다. 이후 맨 위 최신 지시로 이번 범위는 Pi(+ACP)만으로 좁아졌다. durable 내부 장 단위·영속성 판독은 자료로 보존하되 지금 추진하지 않는다. 다른 하네스의 구현 확장도 하지 않는다.

## 착지 전에 열려 있던 질문 — 착지 때의 답

- 정리본을 누가 만들고 Entwurf가 무엇을 하는가: 현재 장 에이전트가 사람과 함께 쓰고, Entwurf는 판 하나를 형식·크기 검사 뒤 바이트 그대로 저장·운반·대조한다. 요약·재구성은 하지 않는다.
- Pi transcript와 backend transcript: 닫힌 장의 원본은 다시 읽지 않는다. 얼개는 완전한 기억이라고 주장하지 않는다. ACP backend 쪽 보존은 측정하지 않았다.
- pi-durable: 범위 밖으로 남았다(ROADMAP).
- 종료·마지막 쓰기·commit point: 위 '전환'의 순서와 같다. 시각은 원본의 기록을 읽고, 매끄럽게 메우지 않는다.
- 최소 필드·크기·rollout: 판 전체 32,768 UTF-8 바이트 상한 하나(모델·백엔드 구분 없음). 2026-11-17 KST에 dist를 다시 빌드하고 Claude Code 연동을 두 설정 폴더에 다시 설치한 뒤 `setup`을 돌렸고, 설치 사본 11곳을 checkout·dist와 바이트 대조했으며, doctor와 `pnpm check`·`check:full`(`568a5df6`)이 통과했다. 그다음 GLG가 전체를 끄고 다시 켰다(GLG 직접, 운영코디 전달). 재시작 뒤 모든 참여 프로세스의 실행 바이트를 감사한 기록은 없다. 첫 실제 쓰기는 2026-11-19 23:28 UTC(11-20 08:28 KST)의 SOL renew다. L1 감사의 owner reader 성공은 reader 하나의 관측이지 전체 rollout의 증거가 아니다. schemaVersion은 그대로다.
