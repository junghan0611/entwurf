# Durable native support — direction and boundary

## Decision and working surface

Support `pi-durable` as a separate native-harness contact, not an enhancement to ordinary Pi. There is no upstream PR or upstream acceptance dependency. **Released 0.31.0** retains Pi1.0.2/source `cd32f7725fdbddbaecdff5b1e68491563394e0ca`. **#132 moved the same supply to Pi 1.1.0** (upstream `abe508e`, carrier bytes unchanged) and shipped it as 0.33.0 at `fea9b3d`; that cut's acceptance and its recorded limits are owned by [CHANGELOG 0.33.0](../CHANGELOG.md) and #132, and none of the 0.32.0 receipts below transfer to it. **#130 /0.32.0 targeted Pi1.0.4 and simpler installation**: the supply contract (P1) and the explicit native-module contract (P2) below are implemented. The frozen `b220b20` candidate's reviewed source, qualification, explicit packed install and required aggregate LIVE floors were accepted on 2026-10-08; pre-version main `78c917a` subsequently passed [exact-SHA CI37679372365](https://github.com/junghan0611/entwurf/actions/runs/37679372365), including its qualification BODY and container axis. At that point the package was prepared as 0.32.0, with its prepared SHA and preserved versioned artifact still owing their own receipts. 0.32.0 was later tagged at `80d66f4` and published; its release and registry acceptance are owned by [CHANGELOG 0.32.0](../CHANGELOG.md) and the [#130 registry-acceptance comment](https://github.com/junghan0611/entwurf/issues/130#issuecomment-6049936030), and none of it transfers to #132.

Development takes place **on a branch in this repository checkout**. No worktrees or tmp development clones. Isolated test fixtures and preserved receipts are evidence, not another implementation authority. `AGENTS.md` owns the working rules. `NEXT.md` takes over the release state and next move at #130 landing; the branch handoff is preserved in the owning issue/evidence and retired before merging. #129 closed at reviewed main `535c2e1` after first native admission; #130 is closed history for runtime-supply; the durable UI and module directory are #134's, and #132's unfinished Herdr alignment is deferred in `ROADMAP.md`.

Expired per-leaf grants and handoffs are not current instructions. They do not prohibit ordinary source edits or builds, or impose a whole-team shutdown/zero-downtime migration as a commit condition. Commits and releases still require the existing verification and authorization boundaries. Push and npm publication require GLG's separate explicit request.

## Ownership

- The native durable SDK owns the engine: execution, scheduler, queues, storage/transcript, compaction, cancellation/recovery, models/auth and internal task/subagent relationships. The app composition around it — settings mapping, prompt/skill assembly, TUI and controllers — is Entwurf's owned source (AGENTS Rule 17).
- **Use what the harness has natively; refuse what it lacks.** Where a harness has a safe official native capability, the contact uses it as-is. Where it has no safe contact point, the contact refuses by name rather than imitate the behaviour with an Entwurf queue, retry or recovery layer. Mail arriving during compaction shows both sides. pi-durable admits the doorbell notice as a native `followUp` submission, which the SDK queues in `pi.inbox` while the conversation has a run (`admitSubmission`); the contact keeps no queue of its own, and the body stays in the Entwurf mailbox until `entwurf_inbox_read`. Ordinary Pi has native steer/followUp for a running turn, but its extension context exposes `isIdle()` and `signal` and no `isCompacting()` (Pi 1.3 `core/extensions/types.d.ts`), and a send during compaction starts a run that races it (#111). So `entwurf-control` refuses it as `compacting`/`busy`; the sender may choose to retry later, and Entwurf adds no automatic retry or queue to Pi. The two receive differently because their native capabilities differ; that is not a defect to equalize. This governs behaviour emulation only. It does not withdraw what Entwurf owns by contract: garden addressing, launch rails, and the thin app/TUI composition supplied under Rule 17.
- Entwurf owns citizen attachment, garden addressing, rail/liveness facts and delivery receipts. One operator-visible host is one citizen; internal conversations/subagents/codemode do not mint additional records.
- The maintained contact is Entwurf's owned app source (emitted as the carrier) plus a narrow bootstrap/adapter. Do not copy the registry/controller assembly into another harness.
- Coordination is a sibling's temporary role, not a higher citizen class or supervisory permission. Do not add queues, automatic retry/restart, backlog managers, credential proxies or recovery apparatus.
- A branch checkpoint commit is not harness admission or release acceptance. Preserve existing focused, package, qualification, frozen FULL, native/LIVE and exact-SHA release requirements; do not invent new proof machinery around the contact.

## Contact and installation

The #147 candidate source adapter defines eight tools: `entwurf_self`, `entwurf_peers`, `entwurf_v2`, `entwurf_inbox_read`, `entwurf_callback`, `entwurf_fresh_call`, `entwurf_resume_call` and `entwurf_retire_call`. Resume reopens a dormant **pi or Claude Code** citizen under that citizen's own garden id (#147 L1, L2); retirement attempts one explicitly operator-requested Pi or Claude Code target, never autonomous cleanup. Only an explicit human-operator request for that target/action authorizes it. Where a host provides or is configured with an approval step, that step applies as well; Pi and pi-durable 1.3.0 have no built-in approval prompt by default. The configured Claude ACP child is also [set to run without per-call permission prompts](./acp-backend-rail.md#configured-claude-acp-permissions); that separate source configuration is not measured ACP retirement. Tool annotations and caller identity are hints and attribution, not permission. The returned action, append-only recording and lock-release results remain distinct, and an unknown result is not permission to replay. Neither tool reopens or retires the durable host itself: pi-durable is a caller, not a supported lifecycle target. Callable schema and actual tool registration, not this prose, establish support. This is candidate-source capability. One dated test-owned [Native round trip](../BASELINE.md#147-native-round-trip-2026-10-22-n1) measured a pi-durable caller actually offering the eight tools and calling retire and resume once per target (n=1); that is not a release gate, coherent rollout or shipment acceptance.

The owned runtime installs extensions before native recovery, provides the required sender-readiness boundary, and exposes root-directed input through the native submission API. Root admission must not change the operator's selected conversation and must propagate native refusal. Runtime internals remain native-owned.

The receive contact is announce-only self-fetch: a fresh mailbox signal submits an untrusted notice to the native root, then the model calls unsafe `entwurf_inbox_read`. The native runtime owns the queue and turn boundary. This is not direct body injection or a new Entwurf queue.

Installation has two independent subjects:

1. **Entwurf package:** the existing npm/source installation surface, compiled adapter, setup and package-consumer checks. The canonical bootstrap/overlay live under `pi/pi-durable/`; a checkout compatibility wrapper is not a second installation API.
2. **Native app/TUI and SDK set:** upstream does not publish the experimental app (installing or upgrading the ordinary Pi CLI does not supply it; `pi-durable` on npm is the library). Since #130 the Entwurf package itself carries the app as a carrier (`pi/pi-durable/carrier/`, emitted from Entwurf's owned source since #141) and declares the pinned SDK set (1.3.0 since #145; 1.2.0 from #141; 1.1.0 from #132) as exact production dependencies; Entwurf verifies both where it is installed and never downloads, repairs or supplies credentials. The released 0.31.0 source-runtime route (an operator checkout at a fixed XDG location) is retired, with no fallback.

[README](../README.md), [setup](setup-clean-host.md#2b-optional-native-durable-pi-durable) and the release notes must describe that distinction and agree with the accepted installation evidence before shipment.

## 0.32 supply and explicit native-module contract (#130)

Supply (P1) and the explicit module ingress (P2) are implemented; candidate-floor acceptance is recorded below, while release floors remain separate:

- **One installation unit (Pi1.0.4 at #130):** supply the omitted upstream durable app/TUI alongside one declared, coherent published SDK version set. The operator does not clone, patch, compile or copy provider model data. Reuse native app/TUI files; native harness semantics stay upstream-owned.
- **Maintainer supply:** pinned upstream commit/tag, declared contact overlay, deterministic emit/import relocation, MIT license, manifest and rebuild equality. A narrow installed-dist resolver connects the omitted app to published libraries. This does not endorse a new harness, sidecar, bundler or updater.
- **Installed verifier:** physical member and member-of-member resolution from the carrier's location must match the declared library set. `npm ls`'s logical tree and directory placement alone are not proof; same-version sharing need not refuse. Carrier drift and incoherent edges refuse by name, with an installation hint. The actual PATH Pi host-version check is separate from this native set check.
- **Measured design input, not1.0.4 acceptance:** intentionally mismatched native1.0.2/host1.0.4 project-local fixtures retained host Pi value/TUI identity. Full exact dependencies still let a unique-name library hoist to a shared root and bind wrong-version libraries. Entwurf-only and isolated npm-global fixtures were coherent. Neither observation certifies an emitted1.0.4 carrier, every package manager, or native admission. Source receipts are recorded in the #130 thread.
- **Explicit native module (P2):** `entwurf pi-durable … --native-module <absolute file>` names ONE operator module, for a new, a `--continue`d or a `--resume`d session. It is an ordinary ES module: its own top-level evaluation (top-level await included) is its initialization, and it completes before the TUI or the runtime is imported — the runtime creates its provider runtime before it installs any extension (owned `runtime.ts:153-159`, the same lines in `carrier/runtime.js`), so environment preparation cannot ride an extension object. Its default export is a native durable `Extension`, installed after the contact, by reference. The ingress checks only a default object with a name, no extension name the app installs itself (`entwurf`, `coding-tools`, `pi-prompt`, `subagent` — a same-name install replaces), and no contact tool name; every other field is the native registry's. On the 1.2.0 SDK set a native tool result's model channel is `output` (#141), renamed from 1.1's `content`. An omitted `output` gives the model the text the tool retained through `api.output()`, and `content` is not read, so a result naming only `content` that retained no output reaches the model as nothing. The identity carriers (`PI_SESSION_ID`, `PI_CODING_AGENT_DIR`, `HOME`, every `ENTWURF_*`) and the process directory are compared across initialization and a change is refused by name; the caller's directory is fixed before the module runs and handed to the app. The module is trusted operator code: these are mistake guards, not a sandbox, and nothing is rolled back. No ambient or default directory, setting, environment variable, persistent profile, automatic retrieval, classic `ExtensionAPI` shim or plugin manager names a module (the operator-named directory form is #134's, below), and `entwurf_fresh_call`'s inputs are unchanged — a fresh sibling gets no module.
- **Mock proof in this release:** the synthetic fixtures `test/fixtures/pi-durable-native-module/` (node:* only; never shipped). The beside lane drives the packaged `main` for order, refusals, the identity and directory guards, the extension order and the bridge spawn *spec*; `check-pi-durable-send`'s `native-module` cell runs the whole `main` on the real carrier with scripted S plus native H — initialization before the first SDK resolution, the module's tool, the native `bash` child seeing the module's value, and the contact answering beside it; `check-pack-install` loads it from an installed package. No real dotenv, secret values, operator settings or credential access.
- **Known host warning (accepted for 0.32):** ordinary Pi warns that host-provided extension packages belong in `peerDependencies`. The exact SDK set is a production dependency on purpose — those installed copies serve the separate native process — and Pi's check reads the manifest's `dependencies`, not module identity. This states a known manifest constraint; it does not certify that every path is harmless. An actual observed problem goes upstream with its evidence.
- **Downstream after release:** agent-config creates and owns the real durable-specific env-loader using the released ingress. Do not put its dotenv policy in Entwurf or modify agent-config in this implementation lane. Existing search/knowledge capability already rides skills/CLI; no andenken port is needed. Native ACP/provider-switch work is deferred.
- **Acceptance:** source-invisible installed runtime/TUI load, affected contact gates and native/LIVE admission on the chosen1.0.4 installation surface remain separate proofs. Existing qualification, frozen FULL and release floors are unchanged.

## #134 paired ingress and task footer

The contract below is proved by its beside claims and their mutants; that lane's PARTIAL receipt is a development measurement, not release acceptance. A release that carries it still owes its own floors — `check:full`, `check-pack-install` (the directory cell included), the `check-pi-durable-send/-contact/-receive` gates, a real terminal, the installed consumer, and the prepared SHA's CI push run (its four required jobs; the qualification body is no longer a release axis, #144) — and its CHANGELOG section records which of them ran. Hard Rule 6 admits the directory form.

- **Paired ingress.** `--native-module <absolute file>` stays as above. `--native-module-dir <absolute directory>` is its paired form, for a new, a `--continue`d or a `--resume`d session; the two are mutually exclusive (one ingress per launch). The named path is resolved once (a symlink to the named directory is followed) and must be a directory. One `readdir`, top level only: a name is selected when it matches `^[^.].*\.extension\.mjs$`; every other name — helpers, dotfiles, tests, subdirectories, directory symlinks — is ignored without being opened or traversed. Each selected name must resolve to a regular file (a file symlink is followed, as the file ingress does). Order is byte-wise by name, never locale. Nothing is watched, recursed, persisted or taken from settings/environment, and a fresh sibling still gets no module.
- **Initialization and guards.** Selected modules are imported in that order, all before the TUI or the runtime is imported, with the identity-carrier and process-directory guard taken around each module and naming its file. A failure at module k leaves modules 1…k-1 already evaluated; the launch refuses and nothing is rolled back — trusted operator code, mistake guards, not a sandbox.
- **Refusals by name.** Path: not absolute, unresolvable, not a directory, no matching entry (an existing plain `index.mjs` is not renamed or discovered, so a directory without a match refuses), a matching entry that is not a regular file, two names resolving to one file. Export: the file ingress's checks, per module. Names: an extension name the app installs itself or a contact tool name (as today), and — new once there is more than one module — two operator modules sharing an extension name or a tool name. The native registry catches neither: `install` replaces a same-name extension silently and validates tool names only within one extension (`@earendil-works/pi-durable` 1.2.0 `dist/harness/registry.js:58-63`; a task-name collision does throw there).
- **Task footer.** The carrier runtime observes the session-wide native task graph for the session's lifetime; `/tasks` toggles only the panel's visibility. The TUI shows a kind-agnostic badge of live background tasks (`node.background`) first in its dock, never shrunk, width-adaptive down to one ASCII character, with non-running states named; with live tasks on a one-row viewport the badge takes that row, and with none the screen is as upstream draws it. A task already terminal leaves the live graph; its outcome is the consumer's report, never an Entwurf ledger (Hard Rule 9). No extension-defined footer slot, second renderer, poller or classic shim is supplied; a formal native UI API is a separate, future decision.
- **Supply.** Both carrier files are emitted from Entwurf's owned source (`pi/pi-durable/src`, #141) by `scripts/emit-pi-durable-carrier.ts`; the generated carrier is never edited by hand. The overlay patch that carried these changes until #141 is retired; its digest stays in the pin's frozen `origin` record.

## #143 minimal coordinator tuning and session selection

The owned reference app forwards `SettingsManager.getTransport()` into the native Harness. As shipped in 0.37.0–0.38.0 it also added `backgroundTokens: 0` to Pi's existing compaction settings, which turned off only the SDK's pre-threshold background compaction (a summary beside a running turn); threshold/overflow compaction kept running inside the turn as the SDK's blocking compaction, and manual `/compact` stayed a conversation-owned native task. #146 removes that override (next section). SDK generation, recovery, persistence, models and auth remain unchanged. `auto` permits continuation only when the provider's body/prefix conditions hold; it does not guarantee every request is a delta or prove lower vendor latency/overload.

The owned prompt lists skills from pi's `skills` setting with each scope's relative path entries read against that scope's own directory — the project's against `<cwd>/.pi`, the global ones against the agent directory — keeping both scopes, the project's first, as pi resolves relative path entries. Absolute and `~` entries are unchanged. Patterns, package skills, `.agents/skills` and skill diagnostics are not part of this mapping. Project trust is not either: the app opens pi's settings with `SettingsManager.create(cwd)`, whose project scope is trusted by default, so a project's settings are read without a trust decision, as before this change; no trust gate is added.

`--resume` reuses the TUI list selector to choose an existing session of the current cwd. The list reads directory names, SQLite/WAL modification times and lock status, not database contents; it shows creation time, garden id when a record exists, native id, last write and open-elsewhere status. Last write sorts descending. Selection opens that exact native session without model override, preserving its existing garden attachment. Cancel opens nothing and exits 0; empty lists, non-terminal input, locked choices and incompatible fresh/continue arguments refuse without falling back. `--continue` remains newest-created-session selection. Both explicit native-module ingress forms apply to resume.

The beside tests exercise the real bootstrap/Harness with sandboxed model and loopback wire oracles. They distinguish transport forwarding/continuation, the compaction policy with blocking/overflow recovery retained (no background summary at #143; the SDK's default background summary since #146), chosen-session reopening and cancellation. These are execution-path proofs, not semantic-memory quality. The #143 issue thread owns review, affected PARTIAL and operator observations; FULL/exact-SHA CI and release/installed-consumer floors remain separate. Memory checkpoints are agent judgment in ordinary conversation, not a new timer, hook, recording service or summary engine.

## Evidence boundaries

Historical source/lab receipts are preserved, not execution dependencies. Accepted initial identity, scripted send success/invalid/reject/R1 and idle receive cells exercised **scripted S + actual native H**, not vendor V or blanket crash/queue certification. Current acceptance must be tied to the actual candidate and the owning verification contracts, not old manifests or a retired coordinator's environment.

- Library reopen/requestId/inbox evidence does not prove end-to-end sender exactly-once or this adapter's complete recovery behavior.
- An interrupted unsafe tool may have partially run. Do not blindly replay it; admission is not completion.
- `readMetaInbox` archives the message and updates mailbox read state before returning. Those side effects do not prove the native tool-result commit; the intervening crash window is not generally certified.
- Startup notices concern fresh `.msg` files, not a promise to drain/replay delivered backlog. Idle receive evidence is not busy/nonroot/backlog/receive-crash acceptance.
- A loopback model driver can exercise native GenerationTask/ToolTask/schema behavior, but cannot replace approved vendor LIVE. Footer/model labels and null record model fields are not billing or actual-model proof.
- Older reader observations certify only the measured subject/time. In particular, an inaccessible proc-root file or a past container snapshot is not proof that an ancestor RW mount is absent or that future readers are supported.

The existing admission path remains identity → native visible identity → send/receive → visible fresh/callback → installed/package and native caller/target/cross-harness LIVE. Apply its declared clauses and matrices; no partial-support state or reduced release floor.
